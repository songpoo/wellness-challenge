# Edge Cases — v4.1 보완 명세

> v4.1 system instruction에서 **명시되지 않은 경계 조건**을 정리한 문서.
> 각 케이스마다 (1) 입력 시나리오, (2) 권장 동작, (3) 결정 필요 사항을 분리해 두었다.
> 결정 필요 사항(❓)은 노바님 컨펌 후 v4.2 instruction에 반영 예정.

---

## 1. 하루에 기록을 여러 번 올릴 때 — 합산 로직

### 1.1 같은 Day의 복수 입력 (정상 케이스)

**입력 예시:**
```
[09:30] "Day 5 아침: 계란 2개 + 토스트 1쪽"
[13:00] "Day 5 점심: 닭가슴살 샐러드, 물 1L"
[19:00] "Day 5 저녁: 연어 + 브로콜리. 운동 HIIT 30분."
```

**권장 동작:**

- **누적(append) 방식이 기본.** 매 입력은 그날 기록의 부분 업데이트로 처리.
- 매 응답은 **누적 상태의 #공식용 리포트**를 출력 (직전 응답의 슈퍼셋).
- `Routine Check`, `Calories (intake)`, `Protein (g)`, `Water (L)`, `Workout Duration` 등 **합산 가능한 필드는 합산**.
- `Sleep (hr)`, `Condition`은 **마지막 입력 우선** (덮어쓰기).
- `Coach Comment`는 매 응답마다 **다시 생성** (당시 누적 데이터 기반).

**충돌 처리:**

| 필드 | 정책 |
| --- | --- |
| 식사 슬롯 (Breakfast/Lunch/Snack/Dinner) | 같은 슬롯 재입력 시 덮어쓰기, 새 슬롯이면 추가 |
| Workout | 여러 번이면 합산 (`"러닝 30분 + HIIT 20분"`) |
| Calories | 항상 합산 |
| Sleep | 마지막 값 우선 |
| Day 번호 | 첫 입력에서 확정, 이후 입력은 같은 Day로 잠금 |

**❓결정 필요:** 슬롯 라벨이 모호한 경우 ("저녁 먹기 전 간식" → Snack인지 Dinner인지) 분류 우선순위?
> **제안:** 시간(HH:MM) 메타데이터가 있으면 시간대로 분류, 없으면 사용자 지정 라벨 우선.

---

### 1.2 #노션용 출력 시 — 어느 시점의 스냅샷인가?

**문제:** 누적 입력 도중 사용자가 `#노션용`을 요청하면, 그 시점까지의 누적분만 JSON으로 나가게 됨. → Notion DB에 **불완전한 row**가 들어갈 위험.

**권장 동작:**

- **#노션용은 "확정(commit)" 의도로만 사용**한다고 instruction에 명시.
- `#노션용 확정`, `#노션용 마감` 같은 키워드를 받으면 그날 기록을 잠그고(lock) 마지막 JSON 출력.
- 잠금 후 같은 Day에 추가 입력이 들어오면: `"Day [X]는 이미 마감되었습니다. 수정하시려면 '수정 Day [X]'라고 말씀해주세요."`

**❓결정 필요:** 마감 키워드 정식 표기? (`#노션용`은 그대로 스냅샷, `#노션용 확정`이 잠금 — 안이 두 갈래)
> **제안:** `#노션용`만 입력 시 → "지금 시점의 스냅샷입니다. 더 추가하실 게 없으면 '확정'이라고 답해주세요." 한 번 확인.

## 2. 중간 수정 (Correction) 시나리오

### 2.1 단일 필드 정정

**입력 예시:**
```
"Day 5 점심 칼로리 잘못 입력했어. 450이 아니라 600이야."
```

**권장 동작:**

- 정정 키워드 자동 감지: `"잘못", "수정", "정정", "사실은", "아니라"` 등.
- 해당 필드만 교체, 다른 누적값은 유지.
- 응답: `"Day 5 점심 칼로리를 600으로 수정했습니다. 변경된 누적: ..."`

### 2.2 전체 Day 재작성

**입력:** `"Day 5 처음부터 다시 기록할게."`

**권장 동작:**

- 확인 한 번: `"Day 5의 모든 기록을 초기화하시겠어요? '네'라고 답해주세요."`
- 확인 후 빈 상태로 리셋, 새 입력 받음.

## 3. Day 번호 불일치 / 점프

### 3.1 시작일 기준 자동 계산과 사용자 입력 충돌

**예시:** 시작일 `2025-11-01`, 오늘 `2025-11-08` (자동 계산 Day 8). 사용자가 `"Day 5 기록"` 입력.

**권장 동작:**

- 자동 계산 Day와 사용자 입력 Day가 다르면 → **과거 기록 추가**로 해석.
- 확인 메시지: `"Day 5 (2025-11-05) 보충 기록으로 처리합니다. 맞나요?"`
- 미래 Day (오늘 Day 8인데 사용자가 Day 12) → `"챌린지 시작일 기준 오늘은 Day 8입니다. Day 12는 4일 후예요. 다시 확인해주세요."`

### 3.2 Day 점프 (Day 5 → Day 9, 6~8 누락)

**권장 동작:**

- 응답에 부드럽게 안내: `"Day 6~8 기록이 비어있네요. 회복 기간이셨다면 'Day 6-8 휴식'이라고 한 번에 기록해주셔도 좋아요."`
- 누락된 날을 강제로 채우지 않음. 통계 계산 시 **결측치는 제외하고 분모도 줄임** (= "기록한 날 기준 평균").

## 4. 시간대(Timezone) 처리

### 4.1 자정 경계

**입력:** 사용자가 `00:30`에 `"Day 5 저녁 라면 먹었어"` 입력. 시계상으론 Day 6.

**권장 동작:**

- 사용자가 명시한 Day 번호를 우선.
- Day 번호 없이 `"오늘"`, `"방금"`, `"저녁"` 같은 모호한 표현이면 → 시계 기준 Day로 해석하되 확인: `"지금이 Day 6 시작인데, Day 5 저녁 기록으로 처리할까요?"`

**❓결정 필요:** "하루의 경계"를 자정으로 할지, 사용자 기상 시각으로 할지?
> **제안:** 기본 자정. 야근/야식 패턴이 잦은 사용자만 온보딩에서 `"내 하루는 03:00에 끝나"` 옵션 활성화.

### 4.2 다른 시간대에서 입력

**케이스:** 출장으로 시간대 이동 (KST → PST).

**권장 동작:** v4.1 범위 외 — **로컬 시간 기준만 지원** 명시. v5에서 고려.

---

## 5. 멀티모달 입력 결측 / 충돌

### 5.1 사진 ↔ 텍스트 정보 충돌

**입력:** 사진은 햄버거 + 콜라, 텍스트는 `"샐러드 먹었어"`.

**권장 동작:**

- 명시적 confirmation: `"사진에는 햄버거가 보이는데, 텍스트는 '샐러드'라고 적혀있어요. 어느 쪽이 맞나요?"`
- 사용자 답변 전엔 분석 보류.

### 5.2 사진만 있고 텍스트 없음

**입력:** 음식 사진 1장만 (캡션 없음).

**권장 동작:**

- v4.1 instruction대로 Vision 분석 후 자동 라벨링.
- 신뢰도 낮으면(예: 음식 종류 추론 모호) → `"이거 [추정음식] 맞나요? 다르면 알려주세요."`

### 5.3 운동 기구 사진 + 시간 없음

**입력:** 트레드밀 사진만, "30분 했어요" 같은 시간 정보 없음.

**권장 동작:**

- 기본값 30분으로 가정하고 명시: `"트레드밀 30분으로 추정했습니다. 다르면 알려주세요."`

## 6. 비현실적 / 의심 입력 강화

v4.1 §예외처리.2의 "10,000 kcal" 케이스를 일반화.

| 필드 | 정상 범위 | 경고 임계 | 거부 임계 |
| --- | --- | --- | --- |
| Calories (intake) | 800 ~ 3,500 | 3,500+ 또는 < 500 | 6,000+ |
| Protein (g) | 30 ~ 200 | 200+ | 500+ |
| Water (L) | 1 ~ 5 | 5+ 또는 < 0.5 | 10+ |
| Workout Duration (min) | 0 ~ 180 | 180+ | 600+ |
| Sleep (hr) | 4 ~ 10 | < 3 또는 > 12 | > 24 |

**거부 임계 도달 시:** JSON Schema validation에서 떨어짐 → `{"error": "invalid_format"}` 반환.
**경고 임계:** 정상 처리하되 Coach Comment에 우려 한 줄 포함.

---

## 7. 통계/리포트 계산 시 결측 처리

### 7.1 주간 평균 계산

- 기록한 날 기준 평균 (`기록일 수 < 7`이어도 그 일수로 나눔).
- 응답에 명시: `"이번 주 4일 기록 기준 평균"` (전체 주의 평균이 아님).

### 7.2 행동 점수의 결측 차원

- 식단 정보가 전혀 없으면 `Goal ① Weight Loss (%)` 배점 중 칼로리 항목(40%)·단백질 항목(30%)을 0이 아니라 **N/A**로 처리.
- 종합 점수 계산 시 N/A 차원은 분모에서 제외.

---

## 8. 챌린지 일정 변경

### 8.1 시작일 변경 요청

**입력:** `"시작일을 2025-11-15로 바꿔줘. 잘못 입력했어."`

**권장 동작:**

- 기존 기록이 있으면 경고: `"Day 1~5 기록이 있습니다. 시작일을 변경하면 모두 Day 번호가 재계산됩니다. 진행할까요?"`
- 확인 후 모든 기록의 Day 재계산.

### 8.2 챌린지 일시 정지 (Pause)

**입력:** `"이번 주는 출장이라 잠깐 멈출게."`

**권장 동작 (v4.1 미지원, v5 후보):**

- v4.1: 일반 휴식일로 처리 (Workout 미수행, 식단 자유).
- v5: Pause 모드 도입 — Day 카운터 정지, 통계 계산에서 제외.

---

## 9. 노션 동기화 실패 / 재시도

> 이 섹션은 봇 자체보단 **Notion 연동 레이어**의 책임이지만, 봇이 알아야 할 부분만 정리.

- 봇은 **JSON 출력만 책임**. 실제 Notion API 호출은 다운스트림 (앱/스크립트).
- 다운스트림에서 동기화 실패 시 사용자가 `"방금 Day 5 노션 안 갔어"` 같이 재요청 → 봇은 **마지막 #노션용 응답을 그대로 재출력** (재계산하지 않음, 멱등성 유지).
